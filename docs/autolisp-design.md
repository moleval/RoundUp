# Инструкция по проектированию AutoLisp

## 1. Локаль и команды

- Приоритетная локаль — русская.
- Пользовательские команды, меню, подсказки, сообщения об ошибках и справка должны быть на русском.
- Новые пользовательские команды приоритетно делать на кириллице.
- Если среда не поддерживает кириллические имена команд, использовать ASCII-псевдоним, но пользовательское описание и подсказки должны быть русскими.

## 2. Кодировки

- Файлы Lisp (`*.lisp`, `*.lsp`, `*.asd`) хранить в кодировке `ANSI Cyrillic / Windows-1251 / CP1251`.
- BOM запрещён.
- Запрещено смешивать разные кодировки в одном файле.
- Русскоязычные текстовые ресурсы, используемые совместно с Lisp, по умолчанию хранить в `CP1251`.
- UTF-8 без BOM допустим только для служебных форматов: `*.md`, `*.json`, `*.yaml`, `*.yml`, `*.xml`, `*.html`.

## 3. Файлы и имена

- Имена файлов и каталогов — только латиницей: `a-z`, `A-Z`, `0-9`, `_`, `-`, `.`.
- Запрещены: пробелы, кириллица, спецсимволы, скобки.
- Рекомендуемый стиль: `lower_snake_case` или `kebab-case`.

## 4. Поля поиска и маски

Использовать следующие переменные для полей поиска:

```text
search_field
search_query
search_mask
search_pattern
```

Служебные символы маски поиска:

| Символ | Значение | Переменная |
|---|---|---|
| `*` | любое число любых символов | `wildcard_any` |
| `?` | ровно один любой символ | `wildcard_char` |
| `#` | ровно одна цифра | `wildcard_digit` |
| `@` | ровно одна буква | `wildcard_letter` |

Требования к поиску:

- Поле поиска должно корректно работать с русским текстом.
- Маска поиска должна поддерживать указанные служебные символы.
- Обработка пустого поля поиска должна быть безопасной.
- Ошибки поиска должны выводиться на русском языке.
- Не должно быть неотловленных ошибок при некорректной маске.

## 5. Отчёты программы в командной строке

- Все отчёты программы в командной строке приводить к табличному структурированному виду.
- Для построения табличного вывода использовать: `|`, `-`, `_`, пробелы.
- Вертикальные черты использовать для разделения колонок.
- Дефисы и нижнее подчёркивание использовать для горизонтальных линий, заголовков и разделителей.
- Пробелы использовать для выравнивания колонок.
- Вывод должен быть читаемым в моноширинном шрифте.
- Ширина колонок должна рассчитываться по содержимому.
- Заголовки таблиц обязательны, если вывод содержит несколько полей.
- Пустые значения не должны ломать выравнивание таблицы.
- Длинные значения не должны разрушать структуру таблицы; при необходимости использовать обрезку, сокращение или перенос по правилам программы.
- Итоговые, предупреждающие и ошибочные сообщения не должны ломать табличную структуру основного отчёта.

## 6. Извлечение свойств динамических блоков — памятка

### Что извлекаем и чем

| Свойство | Метод | Функция проекта |
|---|---|---|
| Эффективное имя | `vla-get-EffectiveName` | `cs-get-effective-name-safe` |
| Видимость | `GetDynamicBlockProperties` → поиск `VISIBILITY`/`ВИДИМОСТЬ` | `cs-get-visibility-safe` |
| Размеры (динам.) | `GetDynamicBlockProperties` → assoc | `cs-block-all-props` + `cs-prop-value` |
| Числовые значения | безопасное преобразование | `cs-value-to-number` |
| Атрибуты | `GetAttributes` → Tag/Text | *(добавить)* |

### Правило №1 — один вызов на блок

```lisp
(setq props (cs-block-all-props obj))   ;; ОДИН раз
(setq w  (cs-prop-value props "Ширина"))
(setq h  (cs-prop-value props "Высота"))
(setq vis (cs-get-visibility-safe obj)) ;; использует тот же принцип
```

Не вызывать `GetDynamicBlockProperties` повторно для каждого свойства. Кэш — по `ename`.

### Правило №2 — имена свойств зависят от локали

```lisp
;; Искать ОБА варианта
(or (cs-prop-value props "Ширина")
    (cs-prop-value props "Width"))
```

### Правило №3 — безопасное преобразование значения

Значения приходят как: число / `VARIANT` / строка `"1234,5"`.

```lisp
(cs-value-to-number val)   ;; из проекта, шаг 3 стабилизации
```

Внутри: запятая → точка, `atof`, без повторной распаковки VARIANT.

### Правило №4 — защита всех ActiveX-вызовов

```lisp
(setq r (vl-catch-all-apply 'vla-get-EffectiveName (list obj)))
(if (vl-catch-all-error-p r) nil r)   ;; nil при ошибке, не падение
```

Сообщения об ошибках — на русском.

### Правило №5 — атрибуты отдельно

```lisp
(if (= (vla-get-HasAttributes obj) :vlax-true)
  (progn
    (setq atts (vlax-invoke obj 'GetAttributes))
    (foreach att atts
      (setq tag (strcase (vla-get-TagString att)))
      (setq val (vla-get-TextString att)))))
```

### Готовая сборка профиля

```lisp
(defun cs-block-full-profile (ent / obj props)
  (setq obj (vl-catch-all-apply 'vlax-ename->vla-object (list ent)))
  (if (vl-catch-all-error-p obj) nil
    (progn
      (setq props (cs-block-all-props obj))   ;; один раз
      (list
        (cons 'name  (cs-get-effective-name-safe obj))
        (cons 'vis   (cs-get-visibility-safe obj))
        (cons 'props props)
        (cons 'w     (cs-prop-value props "Ширина"))
        (cons 'h     (cs-prop-value props "Высота"))))))
```

### Памятка

```
1. Имя        →  vla-get-EffectiveName  (не Name!)
2. Видимость  →  поиск "VISIBILITY"/"ВИДИМОСТЬ" в свойствах
3. Размеры    →  один GetDynamicBlockProperties на блок
4. Число      →  cs-value-to-number (запятая → точка)
5. Атрибуты   →  GetAttributes, только при HasAttributes
6. Кэш        →  по ename, очистка единой функцией
7. Защита     →  все vlax-* через vl-catch-all-error-p
8. Сообщения  →  на русском
```

### По инструкции проекта

- Имена функций — ASCII (`cs-`, `su-`, `n1-`).
- Тексты и команды — русские.
- Кодировка файла — `CP1251` без BOM.
- Системные переменные — сохранить → изменить → восстановить.
- Не оставлять отладочных `princ`.

## 7. Таблицы AutoCAD

### 7.1. Общие требования

- Таблицы AutoCAD должны создаваться программно, через единый механизм или общие функции проекта.
- Не следует формировать таблицы ручным разбросанным рисованием текста и линий, если доступен табличный механизм.
- Подготовка данных и отрисовка таблицы должны быть разделены.
- Таблица должна иметь: заголовок; шапку колонок; строки данных; подытоги групп, если они предусмотрены; общий итог, если он предусмотрен.
- Оформление должно быть единым и централизованным через функции-обёртки (для заголовка, шапки, подытога и итога).
- Повторное создание таблицы должно быть безопасным и не должно приводить к дублированию объектов.
- Если таблица не помещается в заданную область, должно применяться кускование.

### 7.2. Ускоренное создание таблиц

Создание и заполнение нативных таблиц AutoCAD через COM-интерфейс требует подавления промежуточных регенераций, иначе среда пересчитывает геометрию таблицы после изменения каждой ячейки, что критически снижает производительность.

- Перед началом заполнения данных необходимо включить подавление регенерации таблицы (через свойство `RegenerateTableSuppressed` или аналогичный механизм).
- Заполнение ячеек, объединение клеток и применение стилей выполняются при выключенной регенерации.
- После завершения заполнения подавление снимается, что инициирует единственную полную сборку и отрисовку таблицы.
- Вызов принудительного обновления (`Update`) после снятия подавления не требуется и запрещён, чтобы избежать двойной перерисовки.
- Механизм должен быть безопасным: если свойство подавления недоступно в текущей версии среды, должна происходить тихая деградация в стандартный путь без падения программы.

### 7.3. Кускование таблиц

- Большие таблицы должны разбиваться на несколько фрагментов единым математическим алгоритмом.
- Алгоритм работает с плоским списком тегированных строк (например, `data`, `subtotal`) и целевым количеством строк на одну таблицу.
- Инвариант кускования: разрез допускается только перед строкой данных (`data`).
- Строка подытога (`subtotal`) никогда не оказывается первой в новом куске; она всегда остаётся в том же фрагменте, что и последние строки данных своей группы.
- Строки распределяются по частям таблицы максимально равномерно.
- Каждая часть таблицы сохраняет полную структуру: шапку, данные, подытоги и итог.
- Запрещено создавать пустые части таблицы.
- Нумерация строк и итоговые значения должны оставаться согласованными между всеми частями.

## 8. Экспорт табличных данных в XLS и CSV

- Экспорт табличных данных выполнять в XLS как основной формат.
- CSV использовать только как запасной формат при недоступности Excel.
- XLS формировать как Excel-совместимый XML в кодировке `windows-1251`.
- CSV формировать с разделителем `;`.
- Десятичный разделитель в CSV: `,`.
- Стили ячеек должны быть едиными и централизованными.
- Заголовки таблиц должны быть на русском языке.
- Текстовые данные должны экранироваться от XML- и CSV-спецсимволов.
- Запрещено создавать файл с нарушенной структурой, кодировкой или незакрытыми тегами.
- Ошибка экспорта должна выводиться на русском языке и записываться в журнал.

## 9. Формирование формул

- Формулы использовать в XLS-экспорте как основной механизм получения вычисляемых значений.
- В CSV формулы не использовать; выводить только готовые значения.
- В таблицах AutoCAD значения по умолчанию должны быть заранее рассчитаны; живые формулы использовать только если это явно требуется и поддерживается средой.
- Вычисляемые колонки, подытоги и общие итоги должны формироваться единообразно.
- Формулы должны ссылаться только на фактически заполненные диапазоны.
- Запрещено оставлять формулы, которые ссылаются на пустые, удалённые или несуществующие ячейки.
- Вычисляемые значения должны округляться до требуемой точности.
- Подытог группы должен считаться по строкам этой группы.
- Общий итог должен быть согласован с суммой подытогов.

Обобщённые шаблоны формул:

```text
Вычисляемая колонка:
=ROUND(колонка_1 * колонка_2 / масштаб, точность)

Подытог группы:
=SUM(диапазон_строк_группы)

Общий итог:
=SUM(все_подытоги)
```

Для табличных форматов с R1C1-ссылками допустим такой обобщённый вид:

```text
Вычисляемая ячейка:
=ROUND(RC[-2] * RC[-1] / масштаб, точность)

Подытог группы:
=SUM(R[first]C[col]:R[last]C[col])
```

## 10. Экспорт в PDF

- Экспорт области чертежа в PDF должен выполняться через виртуальный PDF-плоттер (например, `DWG To PDF.pc3`) с применением заданных таблиц стилей печати (монохромная или цветная).
- Область экспорта задаётся пользователем путём выделения прямоугольной рамки.
- Координаты окна печати должны передаваться в систему Display Coordinate System (DCS) для корректного позиционирования.
- Формат листа и ориентация (книжная/альбомная) должны подбираться автоматически на основе габаритов выделенной рамки и количества объектов.
- **Сохранение состояния листа**: перед печатью через ActiveX необходимо сохранить текущие настройки активного листа (плоттер, формат бумаги). После завершения экспорта исходные настройки должны быть строго восстановлены.
- **Подавление диалогов**: на время экспорта необходимо подавлять системные диалоги (например, запросы о несоответствии формата бумаги), чтобы избежать прерывания автоматического процесса.
- **Основной и запасной механизмы**:
  - Основной: программная печать в файл через ActiveX (`Plot.PlotToFile`).
  - Запасной: эмуляция командной строки (команда `-ПЕЧАТЬ`), если ActiveX недоступен или завершился ошибкой. При использовании командной строки лента ответов должна формироваться с учётом активной вкладки (Модель/Лист).
- Результат сохраняется во временную или пользовательскую директорию с возможностью автоматического открытия в системном просмотрщике.
- Любая ошибка на этапе настройки окна печати или самого плоттера должна перехватываться, отменять печать и выдавать понятное сообщение на русском языке с указанием этапа сбоя.

## 11. Системные переменные

- Изменять системные переменные только при необходимости.
- Перед изменением сохранять старое значение.
- Восстанавливать значение при любом выходе: успешное завершение; ошибка; прерывание пользователем; аварийное завершение.
- Использовать защитные механизмы: `сохранить → изменить → выполнить → восстановить`.
- Запрещено оставлять системные переменные изменёнными после завершения операции.
- В комментарии указывать: какая переменная меняется; зачем; где выполняется восстановление.

### Аварийное восстановление системных переменных

- Все изменения системных переменных выполнять только через `sysvar_guard`.
- `sysvar_guard` обязан вести реестр изменённых переменных: имя переменной; старое значение; новое значение; имя модуля или команды; причина изменения; время изменения; статус восстановления.
- Для критичных системных переменных до изменения сохранять запись во внешний файл состояния.
- После успешного восстановления запись должна помечаться как закрытая или удаляться.
- При ошибке, отмене пользователем или аварийном завершении команды восстановление должен выполнять `error_handler`.
- Если процесс среды аварийно завершился, восстановление внутри текущей сессии невозможно. В этом случае восстановление должно выполняться при следующем запуске через стартовый модуль или `module_loader`.
- При следующем запуске необходимо проверять незакрытые записи об изменениях системных переменных. Если найдена незакрытая запись: восстановить значение автоматически, если это безопасно; либо вывести понятное предупреждение на русском языке; записать событие в журнал.
- Все действия с системными переменными фиксировать в журнале.
- Запрещено изменять системные переменные вне защитного блока `sysvar_guard`.

## 12. Защитные инструменты

Необходимо создавать и применять внутренние защитные инструменты проверки модулей.

Минимальный набор:

```text
module_loader
syntax_guard
bracket_guard
quote_guard
encoding_guard
eol_guard
debug_guard
sysvar_guard
error_handler
logger
```

Проверки должны выполняться при загрузке программных модулей.

**Перед загрузкой модуля проверять:**

- файл доступен;
- кодировка корректна;
- BOM отсутствует;
- синтаксис корректен;
- скобки сбалансированы;
- кавычки и строковые литералы корректны;
- нет отладочного вывода;
- нет временных файлов;
- изменения системных переменных защищены сохранением и восстановлением.

**Если проверка не пройдена:**

- модуль не загружать;
- вывести понятное сообщение на русском;
- записать ошибку в журнал;
- оставить программу в безопасном состоянии.

**После загрузки модуля проверять:**

- модуль загрузился без ошибок;
- ожидаемые функции или команды доступны;
- повторная загрузка безопасна;
- системные переменные восстановлены;
- основной сценарий работает.

**Дополнительные проверки для таблиц и экспорта:**

- структура таблицы корректна;
- подытоги не оторваны от групп;
- кускование не потеряло строки;
- суммы сходятся;
- экспорт не содержит неэкранированных спецсимволов;
- формулы ссылаются только на существующие диапазоны;
- CSV создан только как запасной вариант;
- настройки листа AutoCAD восстановлены после экспорта в PDF.

## 13. Код от нейросетей

Код, сгенерированный нейросетью или другим ИИ-инструментом, считается недоверенным до прохождения проверки.

Требования:

- такой код проходит все стандартные проверки;
- обязательна проверка при загрузке через внутренние защитные инструменты;
- обязательна ручная проверка человеком;
- сгенерированные модули должны помечаться как ИИ-сгенерированные;
- автоматическая загрузка ИИ-кода без проверок запрещена.

- Пользовательские команды и тексты — на русском.
- Имена должны быть понятными.
- Запрещено оставлять: отладочные принты; временные файлы; закомментированный мусор; неиспользуемые переменные; мёртвый код без пояснений.
- Повторная загрузка кода должна проходить без ошибок.
- Ошибки должны давать понятное сообщение на русском.
- Не хранить в коде: пароли; токены; ключи; абсолютные пользовательские пути.
- Настройки выносить во внешние файлы.

## 15. Форматирование кода, комментарии и маркер редакции

### 15.1. Форматирование кода

- Отступ — 2 пробела. Табуляция не используется.
- Определение функции:

  ```lisp
  (defun имя-функции (арг1 арг2 / локальная1 локальная2)
    ...)
  ```

  Локальные переменные объявляются после `/`.
- Вложенные формы выравниваются по уровню вложенности.
- Скобки должны быть сбалансированы и компактны. Запрещены «висящие» закрывающие скобки на отдельных строках без необходимости.
- Секции кода разделяются комментариями-разделителями:
  - крупный блок:

    ```lisp
    ;; ============================================================
    ;; НАЗВАНИЕ СЕКЦИИ — краткое назначение
    ;; ============================================================
    ```
  - подблок:

    ```lisp
    ;; ------------------------------------------------------------
    ;; НАЗВАНИЕ ПОДБЛОКА
    ;; ------------------------------------------------------------
    ```

### 15.2. Комментарии

- Шапка файла начинается с `;;;` и содержит:

  ```lisp
  ;;; ============================================================
  ;;; ИМЯ_ФАЙЛА.LSP
  ;;; Назначение модуля
  ;;; Зависимости: общие модули, которые используются
  ;;;
  ;;; РЕДАКЦИЯ N: краткое описание изменений
  ;;; ============================================================
  ```

- Пояснения пишутся в стиле «почему», а не «что делает». Очевидные вещи не комментируются.
- Исправления и важные решения фиксируются в комментарии с указанием причины:

  ```lisp
  ;; ВАЖНО: <причина и следствие>
  ```

- Запрещено оставлять закомментированный мёртвый код без пояснения, зачем он сохранён.
- Однострочные комментарии внутри кода начинаются с `;`.

### 15.3. Маркер редакции

Каждый модуль несёт маркер редакции для учёта версий и счётчика загрузчика `RELOAD`.

Формат маркера:

```lisp
(ред. N)
```

где `N` — целое число, увеличиваемое при каждом изменении модуля.

Размещение маркера:

1. В шапке файла:

   ```lisp
   ;;; РЕДАКЦИЯ 28: косметическая переработка — компактная расстановка
   ;;; скобок. Функционал ред. 27 сохранён без изменений.
   ```

2. В строке загрузки модуля:

   ```lisp
   (princ "\nИМЯ_ФАЙЛА.LSP загружен (ред. N: краткое описание). Команды: КОМАНДА1, КОМАНДА2")
   (princ)
   ```

Правила:

- При каждом изменении модуля номер редакции увеличивается на 1.
- Маркер в шапке содержит краткое описание изменений.
- Строка загрузки показывает актуальную редакцию и список доступных команд.
- Версия берётся из переменной модуля, а не зашивается в строку загрузки.
- Изменение функционала без увеличения номера редакции запрещено.
- Косметические изменения (форматирование, переименование без изменения поведения) также требуют увеличения номера редакции.

### 15.4. Связь с критерием готовности

Задача считается выполненной только если:

- код отформатирован по правилам раздела 15.1;
- комментарии соответствуют правилам раздела 15.2;
- маркер редакции обновлён и соответствует фактическим изменениям;
- строка загрузки показывает актуальную редакцию и команды.

## 16. Критерий готовности

Задача считается выполненной, если:

# Требования к выводу при запуске модуля в командной строке

При запуске модуля в командной строке Автокад выводить:

## 1. Описание

2–3 предложения по-русски. Что делает модуль, как запускается.

## 2. Таблица команд

Колонки «КОМАНДА» и «ЧТО ДЕЛАЕТ».

- Команда в виде «EN / RU», если есть английский синоним; иначе только одно имя.
- Описание одной строкой, без переносов, не длиннее 60 символов.
- Только команды из списка выше. Ничего не придумывать.
- Термин «Тег» не использовать.

## 3. Правила выравнивания (моноширинный вывод, как в RELOAD)

- Отступ таблицы: 2 пробела слева.
- Ширина колонки 1 = `max(7, длина самой длинной команды)`.
- Ширина колонки 2 = `max(10, длина самого длинного описания)`.
- Ячейка дополняется пробелами справа до своей ширины.
- Строка: `"| " + ячейка 1 + " | " + ячейка 2 + " |"`.
- Линия: `"+" + дефисы (ширина колонки + 2) + "+" + дефисы (ширина колонки 2 + 2) + "+"`.
- Структура: линия, заголовок, линия, строки, линия.
- Все строки таблицы имеют одинаковую длину.

Пример:

```
  +-----------------------+-----------------------------------+
  | КОМАНДА               | ЧТО ДЕЛАЕТ                        |
  +-----------------------+-----------------------------------+
  | SEARCHATTR / ПОИСКАТР | поиск блоков по атрибутам (окно)  |
  | SEARCHVIS / ПОИСКВИД  | поиск блоков по видимостям (окно) |
  +-----------------------+-----------------------------------+
```
